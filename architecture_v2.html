Batch Worker Reliability — Redis Streams in Detail

Redis Streams with consumer groups give us built-in reliability primitives. Here's the lifecycle of a batch task and what happens when things go wrong:

1
Batch service writes task via XADD — adds a message to the stream containing a chunk of 200 file references. Each message gets a unique, time-ordered ID.
2
Worker reads via XREADGROUP — the consumer group ensures each message is delivered to exactly one worker. The message moves to that worker's Pending Entries List (PEL).
3a
Happy path: Worker ACKs after success — worker processes the chunk, writes results to PostgreSQL, then calls XACK. The message is removed from the PEL. Done.
3b
Worker crashes mid-processing — the message stays in the PEL because it was never ACKed. A supervisor process periodically runs XPENDING to find messages that have been idle too long (e.g., >5 minutes).
4
Supervisor reclaims via XCLAIM — reassigns the stale message to a healthy worker. Increments a retry counter on the message. The new worker processes it as normal.
5
Dead Letter Queue (DLQ) — if a message has been retried N times (e.g., 3) and still fails, it's moved to a separate DLQ stream. This prevents poison messages from blocking the queue. Engineers investigate DLQ entries manually or via alerting.
IDEMPOTENCY
Retries are safe because each task has a unique ID stored in Redis. Before processing, the worker checks: "have I already written results for this task ID?" If yes, ACK and skip. This prevents duplicate work even if a task is delivered twice.
WHY NOT SQS / RABBITMQ?
We already depend on Redis for rate limiting, idempotency keys, and optional embedding cache. Redis Streams give us persistent, consumer-group-aware queuing without adding another infrastructure dependency. One fewer service to operate and monitor.
JWT Authentication — How Customers Prove Identity

JWT (JSON Web Token) lets the gateway verify every request without hitting the database. Here's how tokens are issued, used, and refreshed — and why short-lived tokens don't conflict with long-running batch jobs.

Token Issuance Methods
CLIENT CREDENTIALS
Machine-to-machine. Customer sends client_id + client_secret → gets back a JWT.

Best for: API integrations
This is what Scale AI customers use. No human involved.
AUTHORIZATION CODE (OAuth 2.0)
User logs in via browser redirect → gets auth code → exchanges for JWT.

Best for: Apps acting on behalf of a user
e.g. "Login with Google"
USERNAME / PASSWORD
Client sends credentials directly → gets JWT. Simple but less secure.

Best for: First-party apps only
Not recommended for third-party APIs.
JWT vs API Key — Trade-offs
JWT (OUR CHOICE)
✓ No DB lookup per request — verify signature locally
✓ Carries claims (customer_id, scopes, expiry) inside the token
✓ Scales well — every service can verify independently
✓ Limited damage on leak (short TTL, e.g. 15 min)
✗ Hard to revoke — valid until expiry (need blocklist or short TTL)
✗ More complex — signing keys, refresh flow, expiry handling
API KEY
✓ Simple — generate random string, store in DB
✓ Easy revocation — delete from DB, instant
✓ Good for long-lived external developer integrations

✗ Requires DB/cache lookup on every request
✗ Opaque — no embedded claims, need DB to look up owner
✗ Dangerous on leak — valid forever until manually rotated
Short TTL + Refresh Token Flow
1
Customer authenticates — sends client_id + client_secret to POST /auth/token. Server issues two tokens: an access token (JWT, 15 min TTL) and a refresh token (opaque string, 7 day TTL, stored in PostgreSQL).
2
Customer makes API calls — includes access token in every request header. Gateway verifies the JWT signature and checks expiration. No database hit needed.
3
Access token expires (after 15 min) — customer sends the refresh token to POST /auth/refresh. Server checks refresh token against PostgreSQL → issues a new access token (another 15 min).
4
Need to revoke a customer? — Delete their refresh token from PostgreSQL. Their current access token works for at most 15 more minutes, then they can't refresh. Worst case: 15 min window.
Why Short TTL Works with Long Batch Jobs
Key insight: The JWT authenticates the HTTP request, not the background job. Once the gateway accepts the request, the job runs internally with no token needed.
0:00
Customer sends POST /batch with JWT → Gateway validates ← only auth check
0:01
Batch Service creates job record, writes chunks to Redis Stream, returns job_id ← HTTP request done
0:01–30:00
Workers process chunks internally — no token needed (authenticate at boundary, trust internally)
30:00
Customer calls GET /jobs/{id}/status with a new JWT ← fresh token, no expiry issue
Each HTTP request takes <1 second. The 15-min TTL is plenty. If the token expires between polls, the customer simply gets a new one via refresh token or client credentials.
